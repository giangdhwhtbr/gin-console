# Optional authentication and project access

Epic: gin-console-hlj
Kind: capability
Points: 8 (7 user stories, 16 new REQs plus 1 config REQ and 2 modified: a new auth context with sign-in, sessions, a login rate limiter, per-project access on every project route, a user CLI that writes its own file, and a sign-in screen; security-sensitive; no closed epic with points to anchor)
Date: 2026-11-27

## Why

gin-console has no authentication (README "Warning"). Anyone who can reach the port reads every project and its Beads, and the email on the login screen only selects My work. When the console is shared with more people, or one person should see only some projects, the operator has no way to say who may see what. The feature stays optional: a single-user console behind `tailscale serve` keeps working without a login.

User decisions 2026-11-27:
- **Users:** kept in a separate `users.yaml` managed by a CLI, not in `config.yaml`, so the hand-written config keeps its comments. Passwords are stored as scrypt hashes.
- **Passwords:** always generated by the CLI as strong random passwords and printed once; there is no option to type one.
- **Access:** each user has a list of project names, or `"*"` for all.
- **Refresh:** pulls only the projects of the signed-in user.
- **Sign-in:** replaces the email screen while auth is on; My work uses the user's email from the server. While auth is off the email screen stays.
- **Rate limiter:** on failed sign-ins, per username and per client IP, thresholds in config, in memory.
- **Sessions:** a random token in an `HttpOnly`, `SameSite=Strict` cookie, held in server memory; a restart signs everyone out.

Assumptions (defaults taken without a question):
- Defaults: `session_ttl` 12h, `rate_limit` 5 failures per username and 20 per IP in a sliding 15-minute window.
- The client IP is the one uvicorn reports. uvicorn takes `X-Forwarded-For` only from a proxy on `127.0.0.1` (its default `forwarded_allow_ips`), which covers `tailscale serve`; so the confirmed `trust_forwarded_for` switch is dropped. When the proxy sends no `X-Forwarded-For`, every client shares one IP and the per-IP limit acts as a global one; the per-username limit still applies.
- A locked username or IP gets 429 even with the right password until the window lets a failure fall out; a successful sign-in clears the username counter, not the IP counter.
- An attacker who knows a username can keep it locked; accepted for a small trusted team.
- Usernames match `[a-z0-9][a-z0-9._-]{0,63}`; the CLI lower-cases them.
- Generated passwords: `secrets.token_urlsafe(18)`, 24 characters, about 144 bits. scrypt with n=2^14, r=8, p=1 and a 16-byte salt; the entropy of the password, not the cost factor, carries the strength.
- A project that is not allowed answers 404, the same as an unknown project.
- The CLI reads `config.yaml` (`GIN_CONSOLE_CONFIG`) to find `users_file` and the project names; it works while `auth.enabled` is false so users can be prepared first.
- `/api/health` stays open, for the deploy health check.

Plan decision 2026-11-27: a sandboxed mockup loads its files with no session cookie (opaque origin, so `SameSite` cookies are not sent), so mockups load through a per-session grant in the path, `/api/requirements/mockups/<project>/g/<grant>/files/...` (REQ-AUTH-016; modifies REQ-SERVER-012 and REQ-REQUIREMENTS-010).

## What Changes

- **Config:** an optional `auth` section (`enabled`, `users_file`, `session_ttl`, `rate_limit`).
- **Backend:** a new `auth` context: users file reader with reload on change, password hashing, in-memory sessions, a login rate limiter, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, a middleware that requires a session on `/api/*`, and an allowed-projects filter on every project route, the project list, the overview and refresh.
- **CLI:** `python -m gin_console user add|passwd|assign|unassign|remove|list`.
- **Frontend:** a username and password sign-in screen, a Sign out action, My work from the signed-in user, and a return to sign-in on any 401.
- **Docs:** README security section, ADR 0005.

## User Stories

### US-1: Keep running without a login
As an operator running the console for myself, I want it to work as today unless I turn auth on, so that nothing changes for a single-user setup.
REQ: REQ-AUTH-001, REQ-CONFIG-009

Acceptance criteria:
- A config without `auth`, or with `auth.enabled: false`, serves every API route without a session.
- The email screen still selects My work.

### US-2: Sign in
As a console user, I want to sign in with my username and password, so that only people I trust read the projects.
REQ: REQ-AUTH-002, REQ-AUTH-003, REQ-AUTH-005, REQ-AUTH-006, REQ-AUTH-014, REQ-AUTH-015

Acceptance criteria:
- With auth on, the console shows a sign-in screen and no API data before sign-in.
- A right username and password opens the console, with My work for my email.
- A wrong username or password shows one message that does not say which was wrong.
- Sign out returns to the sign-in screen and the old cookie no longer works.
- When my session expires, the next request returns me to the sign-in screen.

### US-3: Stop password guessing
As an operator, I want repeated failed sign-ins to be refused for a while, so that nobody can guess a password by brute force.
REQ: REQ-AUTH-004, REQ-CONFIG-009

Acceptance criteria:
- After 5 failures for one username within 15 minutes, further attempts for it answer 429 with `Retry-After`, even with the right password.
- After 20 failures from one IP within 15 minutes, further attempts from it answer 429.
- The sign-in screen says when to try again.
- The thresholds come from the config.

### US-4: See only my projects
As a user assigned to some projects, I want to see only those projects, so that other teams' work stays private.
REQ: REQ-AUTH-007, REQ-AUTH-008, REQ-AUTH-016, REQ-SERVER-012, REQ-REQUIREMENTS-010

Acceptance criteria:
- The project switcher and the overview list only my projects.
- Any route of another project answers 404.
- Refresh pulls only my projects.
- A user with `"*"` sees every project.
- Confirmed mockups of my projects still load with their styles and scripts.

### US-5: Create a user with a strong password
As an operator, I want a command that creates a user and prints a generated strong password, so that I never have to invent or hash one.
REQ: REQ-AUTH-010, REQ-AUTH-013

Acceptance criteria:
- `user add` writes the user with a scrypt hash and prints the password once.
- The users file is readable only by its owner.
- An unknown project name or a taken username is refused without writing.

### US-6: Manage users and their projects
As an operator, I want commands to reset a password, assign and unassign projects, remove and list users, so that I can manage access without editing YAML.
REQ: REQ-AUTH-011, REQ-AUTH-012, REQ-AUTH-013

Acceptance criteria:
- `user passwd` prints a new generated password; the old one stops working.
- `user assign` and `user unassign` change the user's projects.
- `user remove` deletes the user.
- `user list` shows name, email and projects, never a hash.

### US-7: Changes apply without a restart
As an operator, I want a user change to take effect on the running console, so that a removed user or a reset password is locked out at once.
REQ: REQ-AUTH-009

Acceptance criteria:
- After `user passwd` or `user remove`, that user's open sessions answer 401 on their next request.
- After `user unassign`, the project disappears from that user's next request.
- A broken users file keeps the last good users and logs an error.

## Non-goals

- OIDC, SSO, or identity headers from a proxy.
- Access rules inside a project (per bead, per page).
- Sessions that survive a restart.
- Managing users from the web UI, or users choosing their own password.
- Roles or an admin user.

## Success Criteria

- With auth off, the existing backend and frontend tests pass unchanged.
- With auth on, no `/api/*` route except `health`, `auth/login` and `auth/me` returns data without a session.
- A user assigned to project A gets 404 on every route of project B, and B is absent from `/api/projects/beads` and `/api/overview`.
- The 6th failed sign-in for one username within the window answers 429.
